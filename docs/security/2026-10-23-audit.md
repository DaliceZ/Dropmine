### F1 — ล้างไฟล์ที่ยังไม่ได้บันทึกได้โดยไม่ต้องยอมรับคำขอใหม่

ตำแหน่ง: `frontend/src/services/DropmineService/index.ts:357–378` โดยเรียก `clearDownloads()` ที่บรรทัด 363 และการล้างยัง revoke URL ของ ZIP ด้วย

เมื่อรายการเดิมสำเร็จแล้ว ผู้โจมตีส่ง `request` ที่ผ่านสิทธิ์การค้นพบตามปกติได้ ตัวรับจัดการ `incoming` ด้วยการล้างไฟล์เก่าทันที จากนั้นจึงแสดงคำขอใหม่ให้ตัดสินใจ แม้ผู้รับปฏิเสธคำขอใหม่ ไฟล์เก่าก็ไม่กลับมา

**หลักฐาน:** ทดสอบถ่ายโอนไฟล์จริงระหว่าง Chromium สองเครื่องจำลองจนมีลิงก์ `unsaved-private.txt` แล้วให้ WebSocket client ตัวที่สามส่งคำขอ ผู้รับยังไม่ได้กดยอมรับ แต่ลิงก์บันทึกเดิมหายไปแล้ว การทดสอบระดับ service ยืนยันเพิ่มเติมว่า Blob URL เดิมถูก revoke ไม่ใช่แค่ซ่อนปุ่ม

**ผลกระทบ:** ผู้รับเสียสำเนาชั่วคราวที่ยังไม่ได้บันทึก ต้องให้ผู้ส่งส่งใหม่ ไม่ได้ลบไฟล์ต้นฉบับจากเครื่องผู้ส่งหรือไฟล์ที่บันทึกลงดิสก์ไปแล้ว

**แนวแก้:** แยกข้อมูลคำขอที่รอตัดสินใจออกจากชุดไฟล์ที่รับสำเร็จ ผูก Blob/ZIP กับรหัสรายการเดิม และอย่าล้างจากข้อความที่อีกฝั่งส่งมา การแทนที่ชุดเดิมต้องเกิดหลังการกระทำที่ผู้รับยืนยัน โดยแจ้งให้บันทึกไฟล์เดิมก่อน

**เกณฑ์ทดสอบหลังแก้:** ส่งคำขอใหม่แล้วปฏิเสธ/ผู้ส่งยกเลิก/หมดเวลา ลิงก์เดิมและ ZIP เดิมยังดาวน์โหลดได้และมีข้อมูลตรงต้นฉบับ

### F2 — ประวัติไม่จำกัด เปิดทางให้ก่อกวนหน่วยความจำและการแสดงผล

ตำแหน่ง: `frontend/src/services/DropmineService/index.ts:87–90`, `frontend/src/components/TransferHistory/index.tsx:31`

ทุก `incoming` ถูกเพิ่มลง `history` การยกเลิกเก็บรายการนั้นไว้ และ UI render ประวัติทั้งหมด ไม่มีเพดานจำนวนรายการหรือจำนวน metadata และไม่มี cooldown เฉพาะการส่งคำขอหาเป้าหมายเดิม

**หลักฐาน:** WebSocket client ส่งคำขอแล้วกดยกเลิก 25 ครั้งผ่าน backend จริง ผู้รับไม่ได้ยอมรับคำขอเหล่านี้ แต่ DOM มี 26 รายการรวมรายการปกติเดิม การทดสอบ service 1,000 รอบพบประวัติ 1,000 รายการและ metadata 50,000 ไฟล์โดยไม่มีการตัดทิ้ง

**ข้อจำกัดหลักฐาน:** การทดสอบ 1,000 รอบเป็นการเรียก service ในเครื่อง ไม่ใช่หลักฐานว่าข้าม rate limit WebSocket ได้ การทดสอบผ่านเครือข่ายจริงใช้ 25 รอบซึ่งยังอยู่ภายใต้เพดานเดิม ไม่ได้ทดสอบจนเบราว์เซอร์หมดหน่วยความจำ

**แนวแก้:** จำกัดประวัติ เช่น 100 รายการ พร้อม pagination/virtualization เมื่อจำเป็น เพิ่ม cooldown ของคำขอและทางเลือกบล็อกผู้ส่ง การลบ metadata เก่าออกจากประวัติต้องไม่ revoke ไฟล์ที่ผู้ใช้ยังเก็บไว้สำหรับดาวน์โหลด

**เกณฑ์ทดสอบหลังแก้:** คำขอ 1,000 รอบเก็บประวัติไม่เกินเพดาน ผู้ใช้ยังใช้งานหน้าได้ และผู้ส่งคนเดิมไม่เปิดคำขอซ้ำได้ทันทีหลังยกเลิก

### F3 — เพดาน 200 MiB ไม่ครอบคลุมจำนวนข้อความ/objects ของ WebRTC

ตำแหน่ง: `frontend/src/services/DropmineService/index.ts:585–601`

ตัวรับตรวจว่าจำนวนไบต์สะสมไม่เกินขนาดที่แจ้ง แต่รับ `ArrayBuffer(0)` และเก็บลง `chunks` ได้ไม่จำกัด ข้อความแต่ละอันยังเลื่อน watchdog แม้ไม่ได้รับข้อมูลเพิ่ม จึงไม่หมดเวลาจากการไม่คืบหน้า นอกจากนี้ chunks ขนาดเล็กมากอาจทำให้ค่าใช้จ่ายต่อ object สูงกว่าขนาดเนื้อไฟล์มาก

**หลักฐาน:** ในรายการที่จำลองว่าได้รับการยอมรับแล้ว ประกาศไฟล์ 0 ไบต์ ส่ง `file-start` และ buffer ว่าง 50,000 ครั้ง ตัวรับเก็บ 50,000 objects โดย `receiveBytes === 0` และไม่มีการปฏิเสธ ทดสอบเพิ่มด้วย RTCPeerConnection สองฝั่งใน Chromium ยืนยันว่า DataChannel จริงส่งและรับ binary message ขนาด 0 ไบต์ได้ การทดสอบ transport นี้แยกจากการทดสอบการสะสม 50,000 objects ของ service

**ผลกระทบ:** ผู้ส่งที่ผู้รับยอมรับไว้สามารถเพิ่มการใช้ RAM/CPU และอาจทำให้แท็บค้างหรือปิดได้ ไม่ใช่การรันโค้ดบนเครื่องหรือการอ่านไฟล์อื่น ไม่ได้ทดสอบจนแท็บ crash

**แนวแก้:** บังคับขนาด chunk ตาม protocol ปัจจุบัน คือ 16 KiB ยกเว้น chunk ท้ายซึ่งเท่ากับไบต์ที่เหลือ ปฏิเสธ binary chunk ว่างและข้อความผิดลำดับก่อนเก็บข้อมูล เพิ่มเพดานขนาดข้อความควบคุม จำนวน chunk และ data channel และเลื่อน timeout เฉพาะเมื่อเกิดความคืบหน้าที่ถูกต้อง

**เกณฑ์ทดสอบหลังแก้:** buffer ว่าง/1-byte flood/ข้อความควบคุมใหญ่/ช่องข้อมูลเกินหนึ่งช่องถูกปฏิเสธอย่างมีขอบเขต ขณะที่ไฟล์ว่างจริงซึ่งส่งเพียง `file-start` และ `file-end` ยังรับได้

### F4 — Health endpoint เพิ่มงาน Redis โดยไม่มีการควบคุมในตัวแอป

ตำแหน่ง: `api/health.ts:10–18`

ทุก invocation สร้าง Redis client ใหม่ เชื่อมต่อ PING แล้วปิด โดยไม่มี cache, single-flight หรือ HTTP rate limit ใน handler นี้ ตัวจำกัด WebSocket ไม่ครอบคลุม HTTP endpoint นี้

**หลักฐาน:** เรียก handler 20 ครั้งพร้อมกันผ่าน TCP proxy ที่ต่อไปยัง Redis ทดสอบบน loopback พบ Redis TCP connections ใหม่ 20 ครั้ง และ response สำเร็จ 20 ครั้ง

**ผลกระทบ:** เป็นจุดเพิ่ม connection churn, TLS handshakes และ compute/usage บน production ถ้าผู้ให้บริการไม่ได้จำกัดไว้ ไม่มีหลักฐานว่า production ถูกโจมตีหรือโควตาหมดจริง และการทดสอบในเครื่องไม่ได้จำลอง TLS หรือ WAF ของ Vercel

**แนวแก้:** แยก liveness ที่ไม่แตะ Redis ออกจาก readiness ใช้ผล readiness cache ช่วงสั้นพร้อม single-flight/connection reuse ตาม runtime และตั้ง edge rate limit สำหรับ endpoint นี้โดยไม่บล็อก health monitor ที่ใช้งานจริง

**เกณฑ์ทดสอบหลังแก้:** คำขอ readiness พร้อมกัน 20 ครั้งในหนึ่ง instance ใช้การตรวจ Redis ที่แชร์กัน เมื่อ Redis ล่มต้องคืนสถานะไม่พร้อมภายใน timeout โดยไม่เปิดเผยรายละเอียด credentials

### F5 — ตรวจหมดอายุช้ากว่าจุดใช้งานจริงใน RAM mode

ตำแหน่ง: `backend/src/modules/peer/services/peer.service.ts:32–36, 98–103`; รอบ maintenance อยู่ที่ `backend/src/modules/peer/peer.route.ts:80–87`

`requireTransfer()` ตรวจผู้เข้าร่วม แต่ไม่ได้ตรวจ `expires` การตอบรับสามารถต่ออายุรายการที่หมดอายุไปแล้ว หาก maintenance ยังไม่ได้ลบ ในสภาพ event loop ปกติช่องว่างสัมพันธ์กับรอบเก็บกวาด 15 วินาที Redis mode ทำ expiry ใน transaction และ relay ตรวจเวลา จึงไม่ควรเหมารวมว่าพบปัญหาเดียวกันทั้งสองโหมด

**หลักฐาน:** ให้ transfer ใน repo ทดสอบมีเวลาหมดอายุในอดีต แล้วให้ผู้รับเดิมตอบรับก่อนเรียก maintenance ระบบยอมรับและตั้งเวลาใหม่

**แนวแก้:** ตรวจ expiry ในจุดที่อนุญาตทุก action พร้อมจบรายการแบบ timeout อย่างสอดคล้องกัน แทนการพึ่งรอบเก็บกวาดอย่างเดียว

**เกณฑ์ทดสอบหลังแก้:** หลังเวลาหมดอายุ การ accept/signal/complete ถูกปฏิเสธทันทีแม้ไม่ได้รัน maintenance โดยยังไม่ให้บุคคลที่สามใช้งานรายการได้

## มาตรการที่ตรวจแล้วทำงานตามกรณีทดสอบ

- **สิทธิ์:** บุคคลที่สาม respond/cancel/complete/ส่ง signal แทนคู่ส่งไม่ได้ และห้าม relay ก่อนผู้รับยอมรับ ไม่พบ IDOR จากกรณีที่ทดสอบ
- **WebSocket:** ตรวจ Origin และเส้นทางก่อน upgrade; 5 กรณี Origin/route ผิดถูกปฏิเสธ 403; binary message ปิดด้วย 1008, payload เกิน 96 KiB ปิดด้วย 1009, flood ถูกปิดด้วย 1008 มีคิวสูงสุดและ backpressure ฝั่งส่ง
- **Validation:** จำกัด 50 ไฟล์/200 MiB ตรวจ schema ฝั่ง server จำกัดความยาวชื่อและ SDP และแก้อักขระเส้นทางก่อนส่ง metadata
- **XSS:** ชื่ออุปกรณ์และไฟล์ที่มี `<img onerror=...>` แสดงเป็นข้อความใน Chromium ไม่กลายเป็น image element หรือรัน handler ในกรณีทดสอบ ไม่พบ `dangerouslySetInnerHTML`, `eval` หรือการนำ input เหล่านี้ไป shell
- **จับคู่:** token สุ่มจาก 24 bytes อายุ 10 นาที ตรวจ token ที่หมดอายุและ token เก่าหลัง rotate ใช้ URL fragment ซึ่งไม่เป็น HTTP query; token เป็น bearer capability ไม่ใช่การยืนยันตัวตนของบุคคล
- **Redis:** ทดสอบข้าม instance, atomic competing requests, การถอนสิทธิ์ relay, lease/TTL, namespace isolation และ subscription failure ผ่าน ไม่เก็บ bytes ไฟล์ไว้ใน Redis ชื่อไฟล์และ SDP ยังผ่าน signaling/PubSub ชั่วคราว
- **ZIP:** ทำที่เครื่องผู้รับ ไม่ extract archive ที่ส่งมา มีการทำชื่อให้เป็นไฟล์ระดับเดียว แก้ชื่อซ้ำ และตรวจข้อมูลหลังแตก ZIP ด้วยเครื่องมือคนละชุด การทดสอบชื่อไทย/ชื่อซ้ำ/ไฟล์ว่างผ่าน
- **Secrets:** สแกนรูปแบบ private key, GitHub token, AWS access key, OpenAI key และ Redis URL ใน Git ที่เข้าถึงได้ทั้ง 5 commits / 132 unique blobs พบเพียง `YOUR_PASSWORD` ในตัวอย่าง ไม่พบค่าจริงตามรูปแบบเหล่านี้; ไม่พบชื่อ secret ฝั่ง server/Redis credentials/private-key pattern ใน frontend bundle ไม่มี source maps ใน build ที่ตรวจ การสแกนด้วย regex ไม่ครอบคลุม secrets ทุกรูปแบบหรือ refs ที่ไม่ได้อยู่ในเครื่อง
- **Dependencies:** `npm audit --json` รายงาน 0 known vulnerabilities ทั้ง dev/production ณ วันที่ตรวจ ไม่ได้หมายความว่า dependencies ปลอดภัยจากช่องโหว่ที่ยังไม่มีประกาศ
- **Deployment/CI จากไฟล์:** production config บังคับ HTTPS origin และ Redis TLS; มี CSP, nosniff, frame restrictions และ referrer policy; Docker ใช้ non-root; GitHub Actions ใช้ `contents: read` และรันทดสอบ/audit

## ความเสี่ยงเชิงออกแบบและสิ่งที่ยังต้องตรวจบน production

1. ชื่ออุปกรณ์แก้เองได้ และ Public IP เดียวกันไม่ได้พิสูจน์ว่าเป็นเพื่อนหรืออยู่ Wi-Fi เดียวกัน การส่งข้อมูลอ่อนไหวควรมีขั้นตอนเปรียบเทียบรหัส/ยืนยันปลายทาง ตัวเข้ารหัส WebRTC ไม่ได้ยืนยันตัวบุคคลโดยตัวมันเอง
2. ผู้ถือ token จับคู่ได้จนหมดอายุ และการ rotate ไม่ถอนคู่เดิม ไม่มี unpair/block ใน protocol ปัจจุบันตามพฤติกรรมที่ระบุไว้ ควรเพิ่มหากต้องการถอนความเชื่อถือโดยไม่ปิดแท็บ
3. signaling server เป็นส่วนที่ต้องเชื่อถือ เพราะส่งต่อ SDP/fingerprints ไม่มีการตรวจ fingerprint อิสระผ่านอีกช่องทาง จึงไม่ควรกล่าวอ้างว่าแม้ signaling ถูกยึดก็ยังยืนยันปลายทางได้
4. เว็บรับส่งไฟล์ทุกชนิดและไม่สแกน malware ไฟล์ที่ผู้ใช้เลือกเปิด/แตก ZIP ภายหลังอาจเป็นอันตรายได้ Unicode ที่ใช้หลอกชื่อ/นามสกุลยังไม่ได้ถูกเตือนใน UI
5. ต้องยืนยัน TLS certificate, HTTP-to-HTTPS redirect, HSTS/CSP ที่ตอบจริง, WebSocket Origin จริง, proxy chain และการ sanitize forwarded headers ห้ามเปิด Node ตรงต่ออินเทอร์เน็ตขณะ trust forwarded headers ผู้ให้บริการ Vercel ระบุว่าปกติจะ overwrite `X-Forwarded-For` แต่ยังไม่ได้ตรวจ deployment ของโปรเจกต์นี้
6. ยังไม่ได้ตรวจ Redis ACL/สิทธิ์จริง, environment isolation จริง, ผู้มีสิทธิ์เข้าถึง secrets/logs, retention ของ provider, WAF/rate limits, spending alerts, branch protection, MFA และ dependency/container image provenance
7. ไม่มี application security events/metrics ที่เพียงพอต่อการตรวจ abuse จากโค้ดที่เห็น ควรบันทึกเฉพาะผลการบล็อก/อัตรา/ข้อผิดพลาด หลีกเลี่ยงชื่อไฟล์, token, SDP, เนื้อไฟล์ และ raw request
8. ยังไม่ได้ทำ container OS vulnerability scan, production penetration/load test, TLS packet inspection หรือทดสอบ Safari/iPhone/Android เครื่องจริง ไม่มี `.env` หรือ `.vercel/project.json` ใน workspace นี้สำหรับยืนยันค่าระบบจริง

## ผลทดสอบและการทำซ้ำ

ใช้ Node.js `22.22.2` บน WSL ทดสอบ Redis บน loopback โดยปิด persistence ไม่ใช้ Redis production

- `npm run typecheck` — ผ่าน
- `npm run build` — ผ่าน
- `npm test` — 27 ผ่าน; Redis 12 ข้ามตามค่าเริ่มต้น จากนั้นทดสอบแยกตามบรรทัดถัดไป
- `npm run test:redis` — 12 ผ่าน
- `npm run test:e2e:redis` — รันล่าสุดผ่าน 10/10 บน backend สอง instances ที่ใช้ Redis ร่วมกัน (42.7 วินาที)
- `npm audit --json` — 0 known vulnerabilities
- local service/socket probes — ยืนยัน F1–F5 และการบล็อก IDOR/Origin/payload/flood
- local browser probes — ยืนยัน F1, F2, ความเป็นไปได้ของ transport ใน F3 และกรณี escape ชื่ออุปกรณ์/ไฟล์

สคริปต์ audit ยืนยันพฤติกรรมของ commit ที่ตรวจ ไม่ใช่ regression tests ที่คาดหวังว่าช่องโหว่ถูกแก้แล้ว หลังแก้โค้ดต้องเปลี่ยน assertions เป็นพฤติกรรมปลอดภัยที่ต้องการด้วย

```sh
# รันจาก repository root หลัง build โดยใช้เฉพาะ loopback
node --import tsx docs/security/audit-probes.mjs
node --import tsx docs/security/browser-probes.mjs

# ให้ REDIS_SERVER_BIN ชี้ executable ทดสอบเพื่อเปิด probe F4 เพิ่ม
REDIS_SERVER_BIN=/absolute/path/to/redis-server node --import tsx docs/security/audit-probes.mjs
```

รอบแรกของ E2E ข้าม instance ผ่าน 9/10 โดยอีกกรณีไม่พบ app root ระหว่างมี frontend build อีก process ทำงาน การรันซ้ำแยกจาก build อื่นผ่าน 10/10 จึงไม่ได้ใช้เหตุการณ์ครั้งแรกเป็นหลักฐานช่องโหว่ และไม่ได้ยืนยันสาเหตุจาก error trace เพิ่มเติม

## แหล่งอ้างอิง

- [OWASP WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html): ใช้เทียบการตรวจสิทธิ์ทุกข้อความ การจำกัดทรัพยากร และ event monitoring
- [Vercel request headers](https://vercel.com/docs/headers/request-headers): ใช้ตรวจสมมติฐานเรื่อง forwarded IP; ไม่ใช่หลักฐานว่า deployment จริงตั้งค่าถูก
- [RFC 8826 — Security Considerations for WebRTC](https://www.rfc-editor.org/info/rfc8826/): แยกการเข้ารหัสช่องทางออกจากการยืนยันปลายทางและความเสี่ยงจาก malicious peer

รายงานและสคริปต์เป็นผลตรวจเท่านั้น รอบนี้ยังไม่ได้แก้ behavior ของแอป ไม่ได้ deploy และไม่ได้ push
